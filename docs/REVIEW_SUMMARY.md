## 3. Items For Owner Review & Merge

1. **Merged into `prime`: PR #11 (`eab2a23`) and PR #12 (`beae5b7`), both 2026-11-18.**
   - #11 fixed two bugs: a pair whose detector task changed on rescan got a second suggestion row (the pair is now the identity and an open row is reclassified in place), and `reopen` could clear a decision on a report the caller submitted (both reviewer actions now share the self-review check).
   - #12 closed the gap that left correlation manual-only: intake now queues `correlation.scan` in the same transaction as the observation insert, so new reports are actually compared. An idempotent replay queues nothing. It edits `collection/service.py`, which Phase 1 owns, so it was merged as a separate PR after #11.
   - Final combined tree: `ruff check backend` clean, 75 passed / 3 skipped, 78 passed with `ECOWATCH_RUN_POSTGIS_TESTS=1`; CI 3/3 green on both PRs.
   - PR #14's backend job failed on the combined `prime` + `master` tree because Phase 2 and Phase 3 each added a `0003` Alembic revision from the same `0002` parent. `0004_merge_phase2_phase3` joins them as a no-op booking revision; `alembic heads` now reports one head, and the full backend suite passes with and without PostGIS.
2. **Phase 2 decisions made 2026-11-18** (recorded in `docs/PHASE2_TODO.md`, `docs/PHASE2_CORRELATION.md` and ADRs):
   - **pgvector approved (ADR-030)** — `correlation_embeddings` and semantic similarity proceed in the existing PostgreSQL service; `token_similarity` stays the keyword fallback.
   - **Evaluation route: smoke-test only** — the harness has been run on temporary fixtures to prove mechanics; no accuracy claim is made.
   - **Case-side actions owned by the cases module (ADR-031)** — `cross_case`, `promote_to_case`, `merge` and `split` use the two-key rules in `docs/PERMISSIONS_MATRIX.md` §4; correlation stays decision support only.
   - **Re-scan triggers: corrections and evidence uploads** — both now enqueue another `correlation.scan` in the same transaction as the change, implemented in the Phase 1-owned modules on their own branch.
4. **Formal ADR status alignment (`docs/20_Technical_Decision_Records.md`):**
   - `ADR-029` is `Approved 2026-11-18`; optionally promote `ADR-014`–`ADR-016` and `ADR-026`–`ADR-028` statuses from `Proposed` to `Approved` during review.
5. **Security decisions and accepted limitation (2026-11-18, owner-approved for this slice):**
   - **Login rate limiting (ADR-032):** DB-backed reuse of the existing `rate_limit` helper, bucketed by SHA-256 of normalised email + client IP (no raw PII in the key); default 5 attempts per 300 s window and 900 s lockout, configurable through `ECOWATCH_LOGIN_MAX_ATTEMPTS`, `ECOWATCH_LOGIN_WINDOW_SECONDS` and `ECOWATCH_LOGIN_LOCKOUT_SECONDS`.
   - **Public DTO field removal (ADR-033):** `originalLocationWording` is no longer returned by `ObservationPublicSummaryResponse`; the restricted staff/owner DTO still includes it.
   - **Accepted limitation (ADR-032):** logout and 401 clearing are client-only. The stateless HMAC bearer token is not server-side revocable and remains valid until expiry (default 12h), although deactivated users are rejected on every request. Immediate server-side revocation is deferred, not implemented.
   - **No validation claim:** a correlation score remains a ranking signal only; `token_similarity` is the labelled fallback, not a validated semantic model. No source, causation, harm or verification claims.
