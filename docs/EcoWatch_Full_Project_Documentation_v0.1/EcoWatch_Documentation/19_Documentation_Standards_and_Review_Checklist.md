# 19 — EcoWatch Documentation Standards and Review Checklist

**Status:** Proposed working standard for maintaining this package.

## 1. Required depth

Documentation must explain not only what the project does, but why a decision is being made and what consequences follow from it.

For each significant design choice, explain:
- What is proposed or approved.
- Why it is needed.
- How it is expected to work.
- Alternatives considered.
- Benefits and trade-offs.
- Dependencies and risks.
- What evidence would demonstrate success.
- Approval status.

## 2. Status discipline

Never present proposals, assumptions or deferred matters as approved decisions. Use the decision register as the source of truth.

## 3. Technical clarity

Explain technical terms in beginner-friendly language when first introduced. Do not assume the reader knows database design, APIs, geospatial processing, machine learning or deployment.

## 4. Scientific integrity

Distinguish observation, measurement, report, interpretation, reconstruction and prediction. State uncertainty and limitations. Do not invent data, thresholds, validation results or partnerships.

## 5. No prompt packages

This documentation project does not include build prompts, master prompts or coding-agent prompt collections. It should describe the project and its requirements, not replace technical design with instructions to another AI.

## 6. Review checklist

- [ ] Does the document explain its purpose?
- [ ] Are approved and proposed decisions distinguished?
- [ ] Is the rationale clear?
- [ ] Are alternatives and trade-offs discussed?
- [ ] Are dependencies and risks included?
- [ ] Are technical terms explained?
- [ ] Are assumptions and unknowns visible?
- [ ] Are claims supported by evidence or labelled as hypotheses?
- [ ] Are related documents and decision records updated?
- [ ] Does the document avoid claiming that unbuilt or untested features already work?
